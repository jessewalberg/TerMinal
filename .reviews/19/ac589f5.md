## Findings

### 1. Quiesce runs before the kill-switch, so a schedule can start during cutover  [id: a3664e2f  ·  confidence: 9/10]

- **Severity:** high
- **Category:** bug
- **File:** `bin/terminal-cutover:102`
- **Score impact:** correctness -20, conformance -15

**Definition**

The script takes the quiesce snapshot at `bin/terminal-cutover:102-111` and only writes the repo schedule kill-switch later at `bin/terminal-cutover:129-136`. `terminal-cron` checks `readDisabled().has(id)` at `bin/terminal-cron:586-588`, then writes a `status: "running"` record for the repo at `bin/terminal-cron:643-667`. A cron firing that passes the disabled check after the quiesce snapshot but before line 129 is not in the blockers list, continues running, and overlaps the import/untrack/projection steps.

**Reproduction**

Start `terminal-cutover <repo> --apply`; after it prints `quiesce: quiet` but before `schedules disabled`, let launchd invoke a schedule for the same `repoRoot`. That schedule has already passed the kill-switch check, so the later disabled file write does not stop the live run that was missed by quiesce.

**Fix prompt**

Fix `bin/terminal-cutover` so the mutating `--apply` flow disables the repo's schedules before running `quiesceStatus`, and always re-enables the exact `down.changed` ids if quiesce blocks or any later step fails. Keep dry-run read-only, but make the apply order match ADR-0002: preflight -> kill-switch -> quiesce -> import -> untrack -> project -> re-enable. Add regression coverage for apply sequencing, either by extracting an injectable `runCutover` flow or by a CLI integration test that proves quiesce is evaluated after the kill-switch is written and schedules are re-enabled when quiesce refuses.

**Regression test**

Add a test that injects fake `setRepoSchedulesDisabled` and `quiesceStatus` functions and fails if quiesce observes schedules still enabled. Include the live-run refusal path to prove schedules are restored on early exit.

### 2. A projection failure makes `--apply` retries stop before projection  [id: 5e0379f6  ·  confidence: 9/10]

- **Severity:** high
- **Category:** bug
- **File:** `bin/terminal-cutover:143`
- **Score impact:** correctness -20, architecture -10

**Definition**

The apply flow runs `git rm -r -q --cached backlog/` at `bin/terminal-cutover:143`, appends `.gitignore`, and only then invokes `vault.mjs project <slug> --init` at line 148. If projection fails after the first untrack succeeds, the `finally` block re-enables schedules, but a retry re-enters line 143 before it can retry projection. `git rm --cached backlog/` is not idempotent once the index entries are gone; a scratch repo reproduction returned `fatal: pathspec 'backlog/' did not match any files` with exit 128 on the second run.

**Reproduction**

Use a fake `VAULT_TOOLS_PATH` whose `import-backlog --apply` succeeds and whose `project --init` exits 1. The first `terminal-cutover <repo> --apply` imports and removes `backlog/` from the index, then fails at projection. The second run aborts at `git rm --cached backlog/`, so it never reaches the idempotent projection code. This contradicts the runbook's claim that re-running `--apply` completes a mid-apply failure.

**Fix prompt**

Make step 5 in `bin/terminal-cutover` retry-safe. Detect tracked backlog entries with `git ls-files --error-unmatch` or `git ls-files -z -- backlog` and skip `git rm --cached` when there is nothing left to remove; dedupe the `backlog/` `.gitignore` entry; then always continue to `vault.mjs project <slug> --init`. Add an integration test with a fake vault tool that fails projection once, reruns apply, and verifies the second run reaches projection instead of failing on `git rm`.

**Regression test**

Create a temp git repo with tracked `backlog/`, run the cutover CLI with a fake projection failure, then rerun with projection success. The expected result is a `.projection` marker and a single `backlog/` gitignore entry.

### 3. Kill-switch writes can clobber concurrent circuit-breaker disables  [id: 36716dba  ·  confidence: 8/10]

- **Severity:** medium
- **Category:** bug
- **File:** `bin/lib/cutover-core.mjs:87`
- **Score impact:** correctness -10, architecture -10

`setRepoSchedulesDisabled` reads the disabled set into memory at `bin/lib/cutover-core.mjs:87`, mutates it, then overwrites the whole file at line 100. `terminal-cron` uses the same read/overwrite shape for the circuit breaker at `bin/terminal-cron:321-333`. If cron disables schedule B while cutover is disabling or re-enabling schedule A, the later writer can overwrite the other's schedule id. The existing test covers a schedule disabled before cutover starts, but not a circuit-breaker write that lands during cutover.

**Fix prompt**

Make `~/.config/TerMinal/agents/disabled.json` updates concurrency-safe for both `bin/lib/cutover-core.mjs` and `bin/terminal-cron`. Introduce a shared zero-dep helper that serializes updates with a lock file and atomic rename, or uses a retrying read-merge-write discipline that re-reads immediately before commit. Update both cutover and cron to use it. Add a regression test that simulates interleaved cutover disable/re-enable and circuit-breaker disable operations and proves the circuit-broken id remains present.

### 4. Cutover ignores the resolved vault path when invoking vault.mjs  [id: 37fb3c64  ·  confidence: 9/10]

- **Severity:** medium
- **Category:** conformance
- **File:** `bin/terminal-cutover:140`
- **Score impact:** correctness -10, conformance -10

`resolveRoute` returns `{ mode, vaultPath, slug }` and honors `GT_VAULT_PATH` / `settings.vaultPath` at `bin/lib/vault-route.mjs:45-59`. `terminal-cutover` resolves that route at `bin/terminal-cutover:50`, but the dry-run and apply `vault.mjs` calls at lines 123, 140, and 148 do not pass `route.vaultPath` through. The sibling `vault.mjs` reads `PROJECTS_VAULT_PATH` at `/Volumes/home-ext/projects/jessewalberg.com/scripts/vault.mjs:30-32`, so a non-default TerMinal vault setting can be logged by cutover while import/projection still mutate the default vault.

**Fix prompt**

Thread the resolved vault path into every `vault.mjs` invocation in `bin/terminal-cutover`. Pass `env: { ...process.env, PROJECTS_VAULT_PATH: route.vaultPath }` through the `sh` helper for both dry-run and apply import/project calls, and make the dry-run output show the actual vault path being used. Add a test with a fake vault tool that asserts `PROJECTS_VAULT_PATH` equals a non-default `settings.vaultPath` or `GT_VAULT_PATH`.
